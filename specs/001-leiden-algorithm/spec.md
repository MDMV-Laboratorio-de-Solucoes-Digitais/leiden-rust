## User Scenarios & Testing *(mandatory)*

### User Story 1 - Detect communities on a small undirected weighted graph (Priority: P1)

As a data scientist, I want to provide a small undirected weighted graph (file or in-memory structure) and a resolution parameter, and receive a partition of nodes into disjoint, internally-connected communities that maximizes modularity under the Leiden algorithm's connectivity guarantee.

**Why this priority**: This is the core end-to-end value path. Without it, nothing else is meaningful.

**Independent Test**: Load a fixture graph with a known optimal partition, run the algorithm with a deterministic seed, and assert the returned partition matches the expected reference partition (modulo deterministic tie-breaking).

**Acceptance Scenarios**:

1. **Given** a 4-clique plus a 5-clique connected by a single bridge edge and the default resolution parameter, **When** the user runs the algorithm with a deterministic seed, **Then** the system returns a partition in which the two cliques are distinct communities and every community is internally connected.
2. **Given** a single-node graph (one node, no edges), **When** the user runs the algorithm, **Then** the system returns a partition with exactly one community containing that single node and reports no error.
3. **Given** an empty graph (no nodes), **When** the user runs the algorithm, **Then** the system returns an empty partition and a clear "empty graph" indicator rather than failing.

---

### User Story 2 - Tune the resolution parameter and observe reproducibility (Priority: P2)

As a researcher, I want to vary the resolution parameter γ (which controls community granularity) and rerun the algorithm under a fixed seed, and obtain a deterministic partition that changes only as γ changes.

**Why this priority**: Resolution is the primary user-facing knob. Without reproducible, parameter-driven output, scientific comparison is impossible.

**Independent Test**: Run the algorithm on a fixture with γ = 0.5 and γ = 2.0; assert that partitions differ for non-trivial graphs, and that two consecutive runs with identical inputs (graph, γ, seed) return identical partitions byte-for-byte.

**Acceptance Scenarios**:

1. **Given** the same fixture graph, seed, and γ, **When** the algorithm is run twice, **Then** both runs return the same partition.
2. **Given** the same fixture graph and seed but different γ values, **When** the algorithm is run, **Then** the partitions differ on any non-degenerate fixture and both partitions are internally connected (see **Canonical term** in §Key Entities).

---

### User Story 3 - Integrate the algorithm into another Rust program or a script via a CLI (Priority: P3)

As a developer integrating community detection into a larger pipeline, I want a stable public library API and a CLI binary (`leiden`, the non-interactive binary in `plan.md §Project Structure`) that reads a graph from a file and writes the partition to stdout, with structured diagnostics on stderr. The interactive Terminal User Interface binary (`leiden-tui`) is a separate deliverable defined in `plan.md §Project Structure` and is exercised by its own Phase 6 tasks; US-3 covers only the `leiden` non-interactive binary and its library facade.

**Why this priority**: Without an integration surface, the library is research-only. With one, it becomes a reusable tool.

**Independent Test**: Invoke the CLI binary with a fixture file, assert exit code 0, parse the stdout partition, and assert that the partition is valid (every node appears in exactly one community). On invalid input, assert exit code ≠ 0 and a human-readable error message on stderr — no panic trace.

**Acceptance Scenarios**:

1. **Given** a valid graph file, **When** the user runs the CLI binary with the file path and optional flags (γ, seed, `--format text|json`), **Then** the CLI writes the partition to stdout in the selected format (JSON by default, tab-separated text with `--format text`) and one progress summary line per phase transition to stderr (one line for `loaded graph`, one per `iteration <N>`, one for `terminated after <N> iterations`; authoritative regex in `cli-schema.md §1.5.1`), and exits with code 0. Output format details (JSON keys, sort order, exact stderr line format) are defined authoritatively in `contracts/cli-schema.md §1.4` and `§1.5`; the canonical example output is shown in `cli-schema.md §1.7`.
2. **Given** a malformed graph file (negative edge weight, self-loop, dangling node id), **When** the user runs the CLI binary, **Then** the CLI writes a clear, structured error message to stderr identifying the offending line, and exits with a non-zero code; no panic trace is printed.
3. **Given** a graph file that cannot be read (missing path, permission denied, or unreadable directory), **When** the user runs the CLI binary, **Then** the CLI writes a structured error message to stderr identifying the path and the I/O cause, and exits with code 5 per `contracts/cli-schema.md §1.6`; no panic trace is printed.
4. **Given** the CLI is invoked without a `--seed` flag, **When** the user inspects the JSON output, **Then** the `seed` field equals the integer `0` (the CLI-side default per FR-004 and `cli-schema.md §1.2`).

  **Exit codes**: authoritative table in `contracts/cli-schema.md §1.6`; restated in `data-model.md §3.5`.

### Edge Cases

- **Empty graph**: handled per US-1 acceptance scenario 3.
- **Single-node graph**: handled per US-1 acceptance scenario 2.
- **Disconnected graph**: every connected component receives at least one community; no community contains nodes from disconnected components.
- **Zero-edge connected components**: an isolated node, or a connected component with nodes but no internal edges, is treated as **one community per component** containing that component's nodes and is **not** considered `DegenerateInput`. A component with ≥2 nodes but zero internal edges becomes one multi-node community (not multiple singletons). `DegenerateInput` is reserved exclusively for graphs with zero total nodes OR zero total edges (per FR-003a / `data-model.md §1.9`). This is locked by `tasks.md` T035e (`disconnected_components_separated`) which is being extended in v1 to cover the zero-edge case. The single-node zero-edge-total-edges case (1 node, 0 edges total) MUST be classified as one community / NOT `DegenerateInput` (asserted by `tasks.md` T033a).
- **Self-loops and parallel edges**: self-loops are rejected at the input boundary with a clear error rather than silently altering the algorithm's invariants. Parallel edges (multiple edges between the same unordered node pair) are **not** an error and are handled at CSR-construction time; see **FR-001** for the authoritative rule. Callers who need different semantics (e.g. multi-graph) MUST pre-aggregate or pre-filter their input. **Canonical-neighbour-id ordering for parallel edges (definitional authority, closes `$speckit-analyze` finding A4, 2026-08-31)**: for an undirected parallel-edge set between unordered pair `{u, v}` where `u` is added to the internal-index map *before* `v` (per `CsrGraph::from_edges` first-seen order), the surviving single CSR entry lives in `offsets[u]` and the canonical neighbour id is `v` (the first-seen target). The summed weight is the sum of all parallel edge weights; the assertion at `tasks.md` T038a pins both the summed weight and the canonical neighbour id. If two node ids happen to be introduced in different orders across runs, the canonical neighbour id is the first-seen one *within* that run, so the CSR is fully deterministic per input order — there is no tie-break ambiguity.
- **Iteration cap reached before convergence**: the algorithm stops at the cap and returns the partition with the **highest total modularity** seen across the run (definitional authority: FR-003a table), and reports the iteration count; it does NOT continue or panic. "Best" is defined as the partition with the highest total modularity seen across the run; ties are broken by earliest-iteration-wins (the partition with the smallest iteration index), and further ties are broken by smallest-community-count-wins (the partition with the fewest distinct communities). The `RunResult.iterations` semantics for this path (cap value reported, not the iteration at which the best was first observed) are authoritative in FR-003a and locked by `tasks.md` T064 / T047a.
- **Numerical extremes**: zero-weight edges, very large node counts, or pathological weight ratios do not produce NaN, ±∞, or silent overflow in the quality (modularity) computation; the algorithm either completes or returns a typed error.
- **Ties in local-moving, refinement, and aggregation**: ties are broken deterministically (the lowest internal `u32` community id wins, per `tasks.md T057a`); the same rule applies uniformly across all three phases of the outer loop, and two consecutive runs with the same inputs always make the same choices. The aggregation tie-break is an extension of the rule in `Edge Cases → Ties in local-moving` and applies to community-merge decisions in `Aggregation`.
- **Resolution γ ≤ 0**: rejected at the input boundary with a typed error.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST accept an undirected, weighted graph (nodes with stable user-supplied ids that can be any `Hash + Eq + Clone + Ord` type, edges with non-negative `f64` weights) and return a partition of the nodes into disjoint, non-empty communities. The library MUST map user-supplied ids to dense internal `u32` indices and store adjacency in compressed sparse row (CSR) form internally; the user-supplied ids are preserved on output. CSR weights are stored internally as `f64` to match the public weight type. Parallel edges (multiple edges between the same unordered node pair) are summed into a single CSR entry whose weight is the sum of the parallel edge weights, in first-seen order; this is a CSR-construction-time behavior of `CsrGraph::from_edges`, not a validation rejection. The canonical neighbour id of the surviving CSR entry is the first-seen target id (deterministic); the assertion at `tasks.md` T038a pins both the summed weight and the canonical neighbour id. Locked by `tasks.md` T038a (`parallel_edges_summarised_into_single_csr_entry`).
- **FR-002**: The system MUST guarantee that every returned community is internally connected (every community's induced subgraph is connected, per the §Key Entities 'Canonical term' definition).
- **FR-003**: The system MUST accept a resolution parameter γ that defaults to 1.0. γ MUST be a finite, positive `f64`; values ≤ 0, NaN, or ±∞ are rejected at the input boundary with `LeidenError::InvalidGamma(f64)` (see also Edge Cases → Resolution γ ≤ 0, which restates the ≤ 0 case). Locked by `tasks.md` T014 (γ ≤ 0) and T058 (NaN/±∞). (authoritative shape: `data-model.md §1.11`)
- **FR-003a**: The system MUST terminate the outer Leiden loop when **either** the partition is stable across a full local-moving pass with no further modularity improvement **or** an iteration cap is reached. The default iteration cap MUST be 10 (matching Traag et al. 2019). The user MUST be able to override the cap, and the run result MUST report which termination condition was hit and the iteration count at termination. The iteration cap MUST be ≥ 1; values below 1 are rejected with `LeidenError::InvalidIterationCap`. The `iterations` value in `RunResult` reports the iteration index at which the algorithm stopped (i.e., the cap reached when `termination_reason == IterationCap`); the iteration at which the best partition was first observed is not separately exposed in v1. Per-`TerminationReason` `iterations` semantics:

  | `termination_reason` | `result.iterations` value |
  |---|---|
  | `Converged` | Number of completed outer-loop passes (≥ 1 on a non-degenerate input) |
  | `IterationCap` | The cap value supplied (or its default of 10) |
  | `DegenerateInput` | `0` |

  These semantics are locked by `tasks.md` T047a (`runresult_iterations_semantics_per_termination_reason`). **Single source of truth**: the canonical per-`TerminationReason` `iterations` semantics live in FR-003a; `plan.md` and `tasks.md T064 / T047a` reference it.
- **FR-004**: The system MUST accept an optional randomness seed via `LeidenParameters::seed: Option<u64>`; with a fixed seed, the algorithm MUST be deterministic — identical inputs yield byte-identical output partitions. The library default is `seed: None`; the CLI default (per `cli-schema.md §1.2`) is `seed: Some(0)`, applied at the CLI boundary by translating an unset `--seed` flag into `Some(0)` (the integer literal `0`, per `cli-schema.md §1.2`). The `seed` is accepted for forward compatibility only and does not influence the deterministic v1 algorithm (see Assumption: Algorithm variant and §Clarifications 2026-08-30 (seed field)). The `seed` field MUST round-trip through `RunResult::seed` without mutation. Adding a stochastic algorithm variant that consumes the `seed` field MUST require an amendment to `.specify/memory/constitution.md` (see Constitution §Governance 'Amendment procedure'); it is out of scope for v1. **v1 scope**: the algorithm is fully deterministic per Assumptions and Constitution §Determinism; The SC-002 reconciliation (2026-08-31) confirms that in v1 the algorithm does not consume `seed`; therefore the determinism guarantee is independent of the `seed` value supplied.
- **FR-005**: The system MUST compute and expose the modularity (or equivalent Leiden quality value) of the returned partition via the public field `RunResult.quality: f64`.
- **FR-006**: The system MUST expose a public library API sufficient to: load a graph, run the algorithm, retrieve the partition, and retrieve the partition quality, without exposing mutable references to internal algorithm state via the `Leiden` orchestrator's public methods; `CsrGraph` and other value types remain owned and external. **Type-name anchoring**: every library type named in FR-001 through FR-005 and FR-008 (e.g., `CsrGraph`, `Edge`, `NodeId`, `RunResult`, `TerminationReason`, `LeidenError`, `LeidenParameters`) plus the supporting public surface (`Partition`, `Modularity`, `QualityFunction`, `MoveComponents`, `LeidenEvent`, `Phase`, `ThreadingPolicy`) is defined authoritatively in `contracts/library-api.md §1` (re-export list); changes to those names require a coordinated update to `library-api.md`, this spec, and `tasks.md`. The "no `&mut self` on `Leiden` other than builders" guarantee is the **primary contract lock** and is enforced by the runtime test `leiden_public_api_has_no_mut_methods` in `leiden/crates/leiden/tests/us3_library.rs` (authoritative; see `tasks.md` T066a); deletion or weakening of that test is a spec violation. A compile-time sealed-marker block in `lib.rs` (optional, add-only) MAY mirror the runtime test's intent but MUST NOT replace it.
- **FR-007**: The system MUST ship a CLI binary that reads a graph file, runs the algorithm with configurable γ and seed, writes the partition to stdout in a documented output format, and writes progress and error diagnostics to stderr. The output format (JSON default; tab-separated text via `--format text`) is defined authoritatively in `contracts/cli-schema.md §1.4` — canonical JSON form is a single line (no pretty-print, no trailing newline) per `cli-schema.md §1.4.1`. Exit codes, error message formats, and per-format error mapping are defined in `contracts/cli-schema.md §1.5–§1.6` (authoritative), with the full exit-code table in `contracts/cli-schema.md §1.6` (summary in US-3 Acceptance Scenarios). Progress and error diagnostics on stderr MUST be emitted via the `tracing` ecosystem per Constitution §VI; `eprintln!` is forbidden in production code paths. `--log-level error` and `--log-level warn` suppress `info`-level progress lines per `cli-schema.md §1.5` and tasks.md T095b/T095c. **Lint-enforcement cross-reference (single source of truth: Constitution §II, NON-NEGOTIABLE)**: this FR's `tracing`-only mandate is *enforced* by the workspace lints `print_stdout = warn` and `dbg_macro = deny` in `[workspace.lints]` (per `rust-code-rigor.md`, copied verbatim per Constitution §II). Weakening those lints to allow `println!`/`eprintln!`/`dbg!` in production code paths is a Constitution MAJOR amendment and would silently break this FR's contract; the FR MUST be updated alongside any such amendment (remediation for `$speckit-analyze` finding A13, 2026-08-31).
- **FR-007b**: The CLI MUST default to writing a JSON partition to stdout (one object with `gamma`, `seed`, `iterations`, `termination_reason`, `quality`, `threading`, and `assignments: [{"node": <id>, "community": <id>}, ...]`). The `quality` field MUST be a finite `f64` (per FR-005) and the `threading` field MUST be the string `"SingleThreaded"` in v1 (per FR-012). The complete field list is: `gamma`, `seed`, `iterations`, `termination_reason`, `quality`, `threading`, `assignments`. The CLI MUST additionally accept a `--format text` flag that switches the stdout output to tab-separated `<node_id>\t<community_id>` lines sorted by node id; all other formats MUST be rejected with a typed error. **Stdout and stderr are independent streams**: stdout carries ONLY the partition output (JSON object or tab-separated text) and stderr carries ONLY progress lines and error diagnostics. Consumers MUST read stdout only; merging the streams will corrupt the partition output. This applies regardless of `--log-level` (even at `--log-level info`, where stderr is verbose, stdout remains the single-line JSON or sorted text).
- **FR-007a**: The CLI MUST accept an edge-list text format as the **primary** input (lines of `<source_id><separator><target_id><separator><weight>`, default separator tab/comma, with an optional `# nodes=N` header) and MUST additionally accept a JSON adjacency document of the form `{"nodes": [...], "edges": [[<src>, <dst>], ...], "weights": [<f64>, ...]}` (where `weights` is optional and defaults to `1.0` per edge) when the file extension is `.json` or the first non-whitespace byte is `{`. The exact schema is authoritative in `contracts/cli-schema.md §1.3.2`. Format dispatch MUST be deterministic and documented.
- **FR-008**: The system MUST reject malformed input (negative weights, self-loops when disallowed, dangling node ids, invalid γ, invalid iteration cap) at the boundary with a typed error that includes the line number or field name of the offending value; no panic-on-error shortcuts. Additionally, the library MUST NOT contain `panic!`, `unwrap()`, `expect()`, `todo!()`, `unimplemented!()`, `unreachable!()`, or `dbg!()` in any production code path; this is enforced by the `[workspace.lints]` block in `rust-code-rigor.md` per Constitution §III. Self-loops are rejected at both the library boundary (`CsrGraph::from_edges`) and the CLI parser. The single `LeidenError::SelfLoop { line: Option<usize>, node: String }` variant is used at both boundaries: the library emits `line: None` (its `from_edges` API takes an iterator with no line context), the CLI emits `line: Some(N)` for the source line. The `node` field carries the offending user-supplied node id as a string at both boundaries. **Reachability note**: the library's `SelfLoop { line: None }` payload is ONLY reachable when a caller invokes `CsrGraph::from_edges` directly with a self-loop `Edge<Id>` (i.e., bypassing the CLI parser). The CLI parser validates self-loops at T086 BEFORE invoking `CsrGraph::from_edges`, so a CLI user never sees `line: None` for a self-loop — they always see `line: Some(N)`. Library users (other Rust programs calling `leiden::CsrGraph::from_edges`) are the audience for `line: None`. Authoritative shape: `data-model.md §1.11`; payload assertions: `tasks.md` T024a (library, `line == None`) and T081 (CLI, `line == Some(N)`). **Single source of truth**: the authoritative shape of `LeidenError` variants lives in `data-model.md §1.11`; FR-008 and `library-api.md §3` reference it.

Any such deviation MUST carry an inline `// leiden-deviation:` marker and an adjacent `// ref: <citation>` comment, and MUST be audit-tested by `tasks.md` task T138a (`fr009_deviations_are_documented`), which scans `crates/leiden/src/{local_moving,refinement,aggregation,quality,orchestrator}/`.

### Key Entities *(include if feature involves data)*

- **Graph**: A set of nodes (identified by stable user-supplied ids) and a set of edges between them, each with a non-negative `f64` weight. Has a node count, edge count, and total edge weight. The user-visible node id is mapped to a dense internal `u32` index; adjacency is stored as compressed sparse rows (CSR) over those internal indices to keep the local-moving inner loop cache-friendly.
- **Partition**: An assignment of every node to exactly one community, plus the set of distinct communities it implies. Each community is a non-empty subset of nodes that is internally connected.
- **Leiden Parameters**: The triple (γ resolution, randomness seed, iteration cap) supplied to a single algorithm run. Defaults: γ = 1.0, iteration_cap = 10, seed = `None` (library) / `Some(0)` (CLI; the CLI translates the unset `--seed` flag into `Some(0)` at the CLI boundary, per FR-004 and `Clarifications 2026-08-30 (seed field)`). The v1 algorithm is fully deterministic and does not consume `seed`; the value round-trips through `RunResult.seed` verbatim for forward compatibility only.
- **Quality Value**: A single numeric value (modularity or equivalent) that scores a partition against its graph; higher is better for the chosen γ.
- **Canonical term**: throughout this specification, the canonical phrase for the community-connectivity invariant is "internally connected" (each community's induced subgraph is connected). This matches the standard graph-theory definition: a subset S ⊆ V is internally connected iff the induced subgraph G[S] is connected. Synonyms such as "well-connected" or "no disconnected community" are used interchangeably in narrative text but should be understood as referring to the same invariant; the canonical phrase in test names, type documentation, and acceptance criteria is **"internally connected"** without exception.
- **Run Result**: The bundle returned from a single algorithm invocation — partition, quality, iteration count, and termination reason (`converged` / `iteration_cap` / `degenerate_input` in JSON output, corresponding to the PascalCase enum variants `Converged` / `IterationCap` / `DegenerateInput` in Rust per `data-model.md §1.9`).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can detect communities on the `fixtures/lfr_small.edg` reference graph (100 nodes, 500 edges) and obtain a partition in under 5 seconds on a single modern CPU thread, with the partition being byte-identical across consecutive runs at fixed seed and γ. The fixture identity is fixed — any other 100-node/500-edge fixture is out of contract.
- **SC-002**: For every fixture in a curated reference suite (≥ 10 graphs spanning cliques, paths, stars, and known-modular structures), the system returns a partition that is internally connected (no community splits) AND matches the reference partition in **100%** of cases — for every fixture, regardless of whether the reference partition is uniquely determined under the documented tie-breaking rule, and regardless of the `seed` value supplied. The v1 algorithm is fully deterministic per FR-004 and Clarifications 2026-08-30, so 100% match is the only meaningful target; the legacy ≥ 90% clause for non-uniquely-determined fixtures is **reserved for a future stochastic variant and is not a v1 contract**. The curated suite, the per-fixture uniqueness classification (informational only in v1), and the per-fixture reference partitions are defined in `fixtures/*.expected.json`, `fixtures/_classification.json`, and `quickstart.md §2`. The v1 repeated-run assertion is `tasks.md` T116a. T116a uses N=30 independent runs per fixture and asserts 100% match. The curated suite cardinality (≥10 graphs per T007c) is asserted by `tasks.md` T116b.
- **SC-003**: Across 1,000 random weighted graphs with nodes in [10, 1000] and edges in [20, 10000], the algorithm completes without panic, without NaN/±∞ in computed quality values, and without producing a non-internally-connected community, in 100% of cases.
- **SC-004**: The public library API exposes exactly the capabilities described in FR-006, with every public item documented and typed; the CLI binary successfully round-trips a fixture graph file to a parseable partition output in 100% of valid-input test runs.
- **SC-005**: Every malformed input scenario from FR-008 produces a structured, line-referencing error message and a non-zero exit code in 100% of test cases, with no panic traces appearing on stderr.

## Assumptions

- **Target users**: developers and researchers working in Rust on community detection in graphs of moderate size. The ~100k-node / ~1M-edge figure is an editorial order-of-magnitude estimate; it is NOT a contractual scale ceiling — no test rejects graphs above this size. Massive-scale distributed Leiden is out of scope for v1. An interactive TUI binary (`leiden-tui`) is in scope for v1 as a thin adapter over the same library API; ratatui is the rendering framework (pinned per `tasks.md` T006 and Constitution §VII).
- **Input scale**: Single-machine, in-memory. The graph is expected to fit in RAM; out-of-core or streaming Leiden is out of scope.
- **Graph format**: Resolved during clarification — see FR-007a and the `## Clarifications` section.
- **Quality function**: Modularity is the default quality function; alternative Leiden quality functions (CPM, Reichardt–Bornholdt) are out of scope unless added explicitly via a later feature.
- **Algorithm variant**: The deterministic, non-stochastic Leiden variant is the default. Stochastic variants (random refined-node selection) are out of scope unless added explicitly via a feature flag and a constitution amendment.
- **Determinism**: The reference implementation produced by this project MUST match a published reference implementation under deterministic tie-breaking; bit-exact match to any specific reference is a goal but not a hard contract, and equivalence is judged on partition quality within a documented tolerance.

## Clarifications

### Session 2026-08-30

- Q: Which CLI input format should the v1 release support for graph files? → A: Both — CSV/edge-list as primary, JSON adjacency as optional (FR-007a).
- Q: What node-id and adjacency representation should the library use internally? → A: Generic `NodeId` trait (supertraits finalized in the 2026-08-30 clarification below; the current canonical set is `Hash + Eq + Clone + Ord`) mapped to a dense internal `u32` index, with adjacency stored in CSR form (FR-001). Note: this trades implementation complexity for caller flexibility — the trait surface must remain small enough to coexist with the strict lint profile.
- Q: When should the Leiden outer loop terminate? → A: Either convergence or iteration cap, whichever lands first; default cap 10 (FR-003a).
- Q: What edge-weight type should the algorithm operate on? → A: `f64` only (FR-001).
- Q: What format should the CLI binary write to stdout for the resulting partition? → A: Both — JSON default, tab-separated text via `--format text` (FR-007b).
- Q: Should `LeidenParameters` carry a `seed` field given that v1 is deterministic? → A: Yes — `LeidenParameters { gamma: f64, seed: Option<u64>, iteration_cap: u32 }`. The v1 algorithm is fully deterministic (no stochastic refinement) per Assumptions and Constitution §Determinism; the `seed` is accepted for forward compatibility only and is forwarded verbatim to `RunResult.seed` without influencing the algorithm. If a stochastic variant is added later, it MUST be gated behind a Cargo feature flag AND require a separate Constitution amendment. The library default is `seed: None`; the CLI default (per `cli-schema.md §1.2`) is `--seed 0`. Rationale: keeps the CLI surface stable while honoring the deterministic v1 contract; aligns `library-api.md §4` with `data-model.md §1.5` and `cli-schema.md §1.2`.
- Q: What supertraits should the public `NodeId` trait expose? → A: `Hash + Eq + Clone + Ord`. `Hash + Eq` enables the user-id → internal-`u32` map; `Clone` supports the blanket impl and the `RunResult<Id>` payload; `Ord` enables `RunResult::partition` to sort assignments by user-supplied id (FR-001, `library-api.md §7`). This is a tightening of the original `Hash + Eq + Ord` (spec) / `Hash + Eq + Clone` (data-model) wording to a single canonical set.
- Q: When the iteration cap is reached, which partition is returned? → A: The partition with the **highest total modularity** seen across the run. Ties are broken by earliest-iteration-wins; further ties by smallest-community-count-wins. Captured in `Edge Cases → Iteration cap reached before convergence`. This supersedes any earlier informal "best so far" wording.
- Q: How does the deterministic tie-break rule apply beyond local-moving? → A: The lowest-internal-id rule applies uniformly to **local-moving, refinement, and aggregation** (community-merge decisions). Two consecutive runs with identical inputs make identical decisions at every phase. Captured in `Edge Cases → Ties in local-moving, refinement, and aggregation`. The `tasks.md` task `T057a` (`lowest_id_tiebreak_aggregation`) implements the aggregation extension.
- Q: When does the CLI emit exit code 5? → A: When the input file cannot be read at all (missing path, permission denied, unreadable directory, or any other `std::io::Error` from `std::fs::read` / `BufReader::new`). Added as US-3 acceptance scenario 3, with a corresponding test in `tasks.md` `T091a` ("`all_exit_codes_exercised`").
- Q: How is the SC-002 "≥ 90% of cases" target interpreted? → A: 100% match required for fixtures with a unique reference partition under the documented tie-break rule; ≥ 90% across repeated runs (independent seeds at fixed γ) for fixtures with non-unique references. Captured in the rewritten SC-002. (Superseded 2026-08-31 by the SC-002 reconciliation in `speckit-analyze`: in v1, the deterministic algorithm does not consume `seed`, so the ≥ 90% clause is **out of scope for v1** and the 100% match requirement extends to non-unique fixtures as well; the ≥ 90% clause is reserved for a future stochastic variant.)
